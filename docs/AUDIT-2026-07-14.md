# To'Latino — Performance & Security Audit (2026-07-14)

Triggered by a reported **hanging loading spinner** the founder saw "en todos
lados" (Mensajes, Menú de comida, configuración de listado, fotos…). Two
full-codebase passes: **performance** (data layer, all spinner-gated modules,
panel host, migrations, client config) and **security** (all 80 migrations, 7
edge functions, `lib/stripe.ts`, every client write path, committed secrets, the
built bundle).

**Verdict:** the platform's foundation is solid. The spinner had a single root
cause (now **fixed + verified**). Performance is otherwise healthy with clear
scale wins available. Security's RLS/secrets foundation is strong; the real
exposure is concentrated in the **payments amount-trust** path and a few
**over-broad RLS write surfaces** — all in Stripe **test mode** today, all
drafted, to close before real-money launch.

## What was FIXED and SHIPPED in this pass

### P0 — the hanging spinner (root cause + fix) ✅ verified

**Root cause:** `apps/web/src/lib/supabase.ts` created the client with **no request
timeout**. supabase-js runs on `fetch`, which has no default timeout, and no
dashboard query attached an abort signal. On a flaky mobile connection a request
that never gets a response never rejects → the awaiting `setLoading(false)` never
runs → the spinner spins forever. It looked like it happened "everywhere" because
`bizAdmin.loading` (one shared gate) blocks **six** modules at once
(Mensajes/Relacionados/Fotos/Pagos/Horario/Listado); one stalled `businesses`
query blanked them all simultaneously. A secondary aggravator: the gate effect
keyed on the `user` **object**, which `useAuth()` re-creates on every auth event
(token refresh, focus) → `setLoading(true)` re-flashed all six mid-session.

**Fix (client-only, reversible):**
1. **Global fetch timeout** — `supabase.ts` now wraps `fetch` with a 15s
   `AbortController` timeout (honoring any caller signal). Any stalled request
   fails fast → the existing `if (error)` fallback runs → screens show an
   empty/error state instead of spinning forever. One change covers **every**
   query app-wide.
2. **`finally`-clear** in `bizAdmin.tsx` — `loading` is always cleared on the live
   request; no early return (cancel/error) can strand it.
3. **Stable effect key** — `bizAdmin` now keys on `user?.id` (a stable string),
   not the `user` object, so token refresh/focus no longer re-flash spinners.

**Verified in a real browser** (Playwright + El Sabor owner, Mensajes):
- Normal network → conversations render, no spinner.
- Simulated dead `business_conversations` fetch → spinner shows, then **resolves**
  to the "Sin mensajes todavía" empty state within the 15s timeout (was infinite
  before). Screenshots: `spin-normal.png`, `spin-stalled-2s.png`,
  `spin-stalled-18s.png`.

## Performance — remaining (healthy; optimizations, not bugs)

- **P1 · Refetch-on-every-mount, no cache.** Modules are conditionally rendered,
  so switching tabs unmounts/remounts each and refetches from scratch. Lift
  per-business data into a small cache in `BizAdminProvider` (keyed by `activeId`)
  or keep modules mounted and hide with CSS. Removes most perceived slowness.
- **P1 · Auth-event refetch.** `auth.tsx:87-98` makes a fresh `user` object on
  every auth event and calls `loadProfile` twice on mount. Gate `setUser`/
  `loadProfile` on an actual id change. (The bizAdmin half is already fixed above.)
- **P1 · Realtime churn in Mensajes.** `Messages.tsx:72-82` lists `activeId` in the
  deps, so the inbox channel is torn down/re-subscribed each time a conversation
  opens. Move `activeId` to a ref → subscribe once per business.
- **P2 · Pagination / LIMIT.** Several dashboard lists fetch **all** rows for a
  business (conversations, messages thread, reviews, customers, orders, items,
  photos). Add `.limit(...)` + range pagination before a single owner can return
  thousands of rows.
- **P3 · Render.** `Food.tsx` (1,587 lines) and `Customers.tsx` (1,415) are
  monoliths; `Food.tsx:380` sorts on every render (memoize); `Kpi`/`Toggle` are
  defined *inside* their parents (hoist to module scope).
